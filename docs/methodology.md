# How this catalog is built (methodology & provenance)

This page is the honest account of how *Latent Radios* is produced, scored, and checked — so you can calibrate how much to trust any given entry. Read it before you rely on the data for anything that matters.

## What this catalog is — and isn't

It **is** a curated research index: a structured map of which Wi‑Fi/wireless chips can be pushed how far toward a software‑defined radio, with citations. It **is not** gospel, a datasheet, or a guarantee. Silicon revisions, driver bit‑rot, and firmware‑version drift all mean a capability that was real in a paper may not reproduce on your bench today. **Verify before you build.** Every record carries a `status` field and `references[]` precisely so you can check the primary source yourself.

## Provenance: how the data is generated

Full disclosure, because it bears on trust: this catalog is assembled by an **automated multi‑agent pipeline** (Claude Code workflows). Each *research cycle* fans out ~14 independent investigator agents, one per vendor family or topic. Each agent web‑searches primary sources (vendor datasheets, kernel drivers, project repos, academic papers), then returns a prose document plus structured database records. A deterministic ingest step writes the files and merges the records; verification cycles then adversarially re‑check the claims. Cycles run repeatedly, each one adding parts, depth, or corrections.

That model is fast and broad, but it has **characteristic failure modes**, and being explicit about them is part of the methodology:

| Failure mode | How it shows up | How it's caught / corrected |
|---|---|---|
| **Over‑claiming** | A chip marked a higher tier than a single demo justifies | Adversarial **verification cycles** (see below) trace each claim to a primary source and downgrade/annotate; `status` is set to `reported`/`theoretical` |
| **Stale/duplicate part numbers** | The same chip under two ids, or an EOL part as "verified" | Dedup by `id` on merge (newest wins); periodic reconciliation |
| **Vendor‑name drift** | "NXP" vs "NXP Semiconductors" vs "NXP (Marvell)" | A canonicalization pass folds variants to one name |
| **Agents renaming/misplacing files** | A doc lands at an unexpected path, breaking cross‑links | An automated broken‑link check after every cycle; the ingest auto‑remaps stray top‑level paths into `docs/` |
| **Near‑empty or placeholder output** | An agent returns a stub instead of content | Caught by size/spot checks; rewritten by hand (this very page was) |

None of this is hidden. The correction machinery is itself part of the repo — the `verification-tier*.md` docs are the audits, and the [roadmap](roadmap.md) logs each cycle.

## The scoring rubric: the SDR ladder

Every module gets one **`sdr_tier`** (0–5) — the *highest* rung reachable with **public** tooling — and a set of orthogonal **`sdr_capabilities`** flags. The ladder is defined in full in [taxonomy.md](taxonomy.md):

- **0 Black box** — stock only; catalogued when the part is notable but has no public path off the ground floor.
- **1 Monitor + injection** — raw 802.11 (or raw packet) RX/TX.
- **2 CSI** — per‑subcarrier complex channel state.
- **3 Spectral / raw‑PHY scan** — FFT bins across the channel.
- **4 Arbitrary waveform / raw‑IQ TX** — author baseband IQ out the front‑end.
- **5 Open / documented PHY** — open firmware, or a genuine SDR used as the yardstick.

**Judgment calls** are resolved conservatively:
- A capability shown only in a conference demo is scored at its tier but with **`status: "reported"`**, not `verified`.
- "Monitor works, injection is flaky" is **Tier 1 with a note**, not an inflated claim — see the [Tier‑1 injection audit](verification-tier1-injection.md).
- FMCW radar silicon (TI AWR, Infineon BGT) genuinely exposes raw IQ, so it earns **Tier 4** even though it isn't Wi‑Fi — the catalog's scope is "wireless modules usable as an SDR *to some extent*," not "Wi‑Fi only."

## The data model

- **[data/schema.json](../data/schema.json)** — the JSON Schema every record must satisfy.
- **[data/modules.json](../data/modules.json)** — the canonical database.
- **[data/modules.csv](../data/modules.csv)** — a flattened view, regenerated by [scripts/build_csv.py](../scripts/build_csv.py).
- **[scripts/validate.py](../scripts/validate.py)** — checks the DB against the schema, enforces id‑uniqueness and the tier/capability/band/openness enums. It runs after every cycle; the tree is only committed when it passes.

## The `status` field is load‑bearing

- **`verified`** — works with maintained public tooling today (or the maintainer reproduces it).
- **`reported`** — demonstrated in a paper/talk, but not something you can necessarily reproduce off the shelf.
- **`theoretical`** — plausible from the architecture, but unproven.

If you are choosing hardware to *buy and use*, prefer `verified`. If you are surveying what's possible, `reported`/`theoretical` map the frontier.

## Adversarial verification

Claims at each tier are re‑checked by a dedicated audit that tries to *refute* them and traces each to a primary source:

- [Tier‑1 injection audit](verification-tier1-injection.md) — which chips actually inject in practice.
- [Tier‑2 CSI audit](verification-tier2-csi.md) — which CSI toolchains still build/run.
- [Tier‑3 spectral audit](verification-tier3-spectral.md) — which parts really expose spectral scan.
- [Tier‑4 arbitrary‑TX audit](verification-tier4.md) — the strongest evidence for each raw‑IQ‑TX claim.
- [Tier‑5 open‑firmware audit](verification-tier5-openfirmware.md) — which "open firmware" is genuinely open and maintained.

These audits are why the higher tiers are small: the bar is evidence, and a lot of internet lore doesn't clear it.

## How to read the catalog responsibly

1. Start from the [decision guide](which-chip-decision-guide.md) or the capability index for what fits your goal.
2. Check the record's `status` and, for anything you'll depend on, open its `references[]`.
3. Treat tiers as *reachability with effort*, not plug‑and‑play — Tier ≥2 usually means patched firmware, a specific kernel, or an out‑of‑tree driver.
4. Found an error? That's expected and welcome — see [CONTRIBUTING.md](../CONTRIBUTING.md). The one rule is *cite your source.*

*The catalog aims to be exhaustive and honest. Where those two goals conflict, honesty wins — an entry marked "we're not sure" is worth more than a confident wrong one.*
